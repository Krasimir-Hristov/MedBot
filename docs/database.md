# 🗄️ Документация на базата данни: MedBot RAG

Тази документация описва архитектурата, таблиците, векторните индекси и потока на данни в базата данни на **MedBot** (в интерфейса – *MedScan RAG*), работеща на Neon Serverless PostgreSQL.

---

## 1. Общ преглед на архитектурата

Базата данни се хоства в **Neon Serverless PostgreSQL** (регион `aws-eu-central-1` – Франкфурт) за осигуряване на минимална латентност към България 🇧🇬 и Гърция 🇬🇷.

### Основни предимства:
- **Serverless Autoscaling:** Автоматично мащабиране на изчислителните ресурси (Compute) при натоварване и приспиване (Scale-to-Zero), когато няма активност, за максимална икономичност.
- **Вграден Connection Pooler:** Използва се пулърът на Neon (`-pooler.c-7.eu-central-1.aws.neon.tech`), който поддържа хиляди конкурентни връзки без изчерпване на ресурсите при сървърлес заявки от Vercel.
- **Вграден `pgvector`:** Векторно разширение за косинусно търсене на онкологични документи с 1536 измерения.
- **Нулев външен сторидж за файлове:** Документите (~30 бр.) се компресират в браузъра (до 1600px, ~300KB) и се записват директно като `file_base64` в таблицата. Прикачените към лекарските предписания файлове (PDF и изображения) се записват в `attachment_base64` в `doctor_notes`. Това гарантира 100% консистентност (атомарност) между файл, метаданни и семантичен вектор без нужда от външни S3 кофи.

## 2. Структура на таблиците (Data Schema)

| Колона | Тип | Описание |
| :--- | :--- | :--- |
| **`id`** | `SERIAL PRIMARY KEY` | Уникален идентификатор, използван за отваряне на изображението в `/api/doc/[id]`. |
| **`title_bg`** | `TEXT NOT NULL` | Заглавие на документа на български език (напр. *"Епикриза от операция"*). |
| **`title_el`** | `TEXT NOT NULL` | Заглавие на документа на гръцки език (напр. *"Εξιτήριο Χειρουργείου"*). |
| **`doc_date`** | `TEXT NOT NULL` | Дата на провеждане на изследването / документа (формат `YYYY-MM-DD`). |
| **`category`** | `TEXT NOT NULL` | Категория: *Хистология*, *Образна диагностика*, *Туморни маркери*, *Епикризи*, *Лабораторни изследвания*, *Други*. |
| **`summary_el`** | `TEXT NOT NULL` | Кратко клинично резюме на гръцки език, предназначено за лекуващия гръцки лекар. |
| **`metadata`** | `JSONB` | Допълнителни структурирани параметри: `hospital`, `doctor`, `staging`, `keyMarkers[]`, `criticalAlerts[]`, `fileName`. Парсва се безопасно през `parseClinicalMetadata` (никога не се доверяваме на `unknown`). |
| **`extracted_text`**| `TEXT NOT NULL` | Пълен текст от документа, извлечен чрез мултимодалния модел (OCR). |
| **`semantic_text`** | `TEXT` | Двуезичен обобщен текст, използван за генериране на семантичния вектор. |
| **`embedding`** | `vector(1536)` | Вектор от 1536 измерения, генериран от `openai/text-embedding-3-small`. |
| **`file_base64`** | `TEXT NOT NULL` | Base64 кодиран файл – компресиран JPEG (≤1600px, ~350KB) или оригинален PDF (≤10 MB). |
| **`mime_type`** | `TEXT NOT NULL` | MIME тип (`image/jpeg` по подразбиране, или `application/pdf`). |
| **`created_at`** | `TIMESTAMPTZ` | Времева марка на качване в системата. |

### 🗨️ 4. Таблица `chat_messages` (Чат съобщения)
Съхранява съобщенията от всяка сесия. При изтриване на сесия (`ON DELETE CASCADE`), всички нейни съобщения се изтриват автоматично.

| Колона | Тип | Описание |
| :--- | :--- | :--- |
| **`id`** | `SERIAL PRIMARY KEY` | Уникален ID на съобщението. |
| **`session_id`** | `TEXT NOT NULL` | Референция към `chat_sessions(session_id)`. |
| **`role`** | `TEXT NOT NULL` | `user` (лекар или пациент) или `assistant` (AI отговор). |
| **`content`** | `TEXT NOT NULL` | Текст на съобщението. |
| **`citations`** | `JSONB` | Списък с цитирани документи `[{ id, title }]`. |
| **`created_at`** | `TIMESTAMPTZ` | Времева марка. |

## 3. Векторно търсене и HNSW индекси

За бързо и точно намиране на съответните медицински документи и лекарски насоки при запитване от лекаря или пациента, върху колоните `embedding` в двете основни таблици са изградени **HNSW (Hierarchical Navigable Small World)** индекси:

```sql
CREATE INDEX IF NOT EXISTS medical_documents_embedding_hnsw_idx 
ON medical_documents 
USING hnsw (embedding vector_cosine_ops);

CREATE INDEX IF NOT EXISTS doctor_notes_embedding_hnsw_idx 
ON doctor_notes 
USING hnsw (embedding vector_cosine_ops);
```

### Защо HNSW?
1. **Висока скорост на търсене:** Работи в логаритмично време $O(\log N)$ и връща резултати за под 10ms.
2. **Без нужда от предварително обучение (за разлика от IVFFlat):** Работи отлично както за 30 документа, така и при добавяне на нови документи.
3. **Косинусна метрика (`vector_cosine_ops`):** Измерва семантичната близост между ъглите на векторите, игнорирайки дължината на текста:
   $$\text{cosine\_distance}(u, v) = 1 - \frac{u \cdot v}{\|u\|_2 \|v\|_2}$$

> **Бележка за малкия корпус:** При досие от ~30 документа оптимизаторът на PostgreSQL може сам да избере последователно сканиране (sequential scan) вместо индекса — това е коректно и бързо за такъв обем. Индексът е наличен и започва да се използва автоматично при нарастване на таблицата.

## 5. Сигурност и Row Level Security (RLS)

- **RLS е активиран на ниво PostgreSQL за всичките 6 таблици:**
  ```sql
  ALTER TABLE medical_documents ENABLE ROW LEVEL SECURITY;
  ALTER TABLE doctor_notes ENABLE ROW LEVEL SECURITY;
  ALTER TABLE chat_sessions ENABLE ROW LEVEL SECURITY;
  ALTER TABLE chat_messages ENABLE ROW LEVEL SECURITY;
  ALTER TABLE dossier_summaries ENABLE ROW LEVEL SECURITY;
  ALTER TABLE patient_guideline_items ENABLE ROW LEVEL SECURITY;
  ```
  Приложението се свързва с ролята `neondb_owner`, която има атрибут `BYPASSRLS`, затова RLS **не блокира** нормалната работа на сървърния код. Смисълът е защита в дълбочина: всяка бъдеща не-собственик роля (напр. read-only аналитична роля) не може да чете или пише пациентски данни без изрично дефинирани политики.
- **Защита в дълбочина (Defense in Depth):**
  1. Всички заявки се изпълняват **само на сървърно ниво** (Next.js Server Components, Server Actions и API Routes).
  2. Клиентският браузър **няма директна връзка** към Neon базата (No direct client DB access).
  3. Всички критични операции (качване, чат, извличане на документи) преминават през предварителна валидация на ПИН кода или сесийно удостоверяване.


## 6. AI Обобщение на досието и чернови на насоки

### `dossier_summaries`
История на AI обобщенията на цялото досие (гръцки Markdown с цитати `/api/doc/ID`).
`document_ids` съдържа ID-тата на документите, включени в обобщението. С тях се засича остаряване (нови или изтрити документи).

### `patient_guideline_items`
Чернови на насоки за пациента (`category`: diet, exercise, therapy, general; `status`: pending, approved, rejected; `source`: ai, doctor).
**Тази таблица никога не се чете от пациентския портал.** Одобрените точки се превеждат на български и се публикуват като редове в `doctor_notes` само след потвърждение от лекаря.
